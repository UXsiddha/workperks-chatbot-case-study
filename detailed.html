01What I built

An informative assistant over thirteen tools, and the server behind it.

WorkPerks is a corporate benefits app. The assistant inside it says what the company offers, what a benefit covers, and what someone is already holding.

Three weeks of it went on finding where the build met the specification only on paper.

Claude Code wrote every line, and the three specification documents behind it. Section 03 is that process.

0

03How it was built

Three specification revisions in three weeks, each rewritten against what the live systems returned.

Vibe-coded start to finish with Claude Code: the React screen, the server, the thirteen tools, the proxy, the renderer, the test suite, and the three specifications that steered it.

The loop was never specify and accept. It was specify, build, run the result against the live database and the live supplier account, and rewrite the specification against what those returned.

Three revisions in three weeks. The first written before anyone read the schema, the second against the live database, the third once the app proved able to answer from the state it already posts with each question.

Turnaround

Agents were pointed at the build too, not only used to produce it

  1. A separate agent audited the build against the spec

    It found nine defects. One was a guarantee the specification asserted and the code did not provide: route validation was described as failing closed, but validated action buttons only, leaving the row links an employee actually clicks unchecked. No stake in the implementation it reviewed

  2. The held-out questions were written by an agent denied the answer key

    Twenty-five questions phrased as situations, with the search vocabulary file withheld, and the list committed before any were run. A set written by whoever tuned the search measures the tuning rather than the search. Committed first, so it could not be edited into passing

  3. Then the tests themselves were audited

    One instruction: identify checks that pass while the property they assert is false. Four of eight did. One counted apologies in copy that contains none, so it had passed every run while testing nothing, and was deleted rather than repaired. A check counts only once it has been observed failing

The suite is generated from the catalogue, so it cannot fall out of date silently

Every benefit, variant, category and funding type turns into questions on its own, across nine families. Eleven flat rules then read each answer back: no two currencies together, no route that leads nowhere, no unmasked code, no count that disagrees with the rows under it.

04How it works

Five layers, and only one of them is allowed to contain a model.

The model decides which tool. The app decides what the answer looks like. Those two never swap. Every item below is a file or a service that exists in the build.

  1. Client

    The employee’s phone

    Two surfaces, one server.

    • Chat.tsxThe screen. Thread state, every block renderer, the send loop.
    • chat.tsBuilds the context posted with each question: benefits, balances, orders, and the list of screens that exist.
    • chat-shim.jsThe older HTML client. Intercepts the navigation sentinel, anchors the newest message in view.

  2. API route

    Everything before a model runs

    A greeting or a flood never reaches the provider.

    • limit.tsCaps how many turns a conversation gets a minute, before any model runs.
    • isGreeting“hi”, “ok”, “?”, an emoji. Answered without a model.
    • redactForModelThe data boundary. It runs on the server, over whatever the client sent.
    • audit.tsAppend-only trail. Tool, timing, outcome, argument names. Never values, never results.

  3. Decision

    Where the model lives

    Two calls at most, both wrapped against provider failure.

    • classifyIntentSends the rules and thirteen tool schemas. Reads back a tool name and its arguments.
    • composeAnswerOptional. Writes one sentence, thrown away if it states a figure the data does not have, or slips into system voice.
    • withProviderRetries after the delay the provider specifies, then falls back to a second model, then returns null.
    • safetyNetRouteKeyword rules, below the model rather than above it.

  4. Tools

    One switch, thirteen cases

    Data, or the reason there is none.

    • tools/app.tsSeven. Catalogue search, one benefit, definitions, orders, balances, screens.
    • tools/vouchers.tsFour, against the supplier. Code masking lives here.
    • tools/about.tsOne. Eight whitelisted passages about the app itself.

  5. Data and render

    Where facts come from

    One tool result, two outputs, one renderer.

    • appContextPosted by the page. Benefits, balances, orders, screens, search vocabulary.
    • proxy :8787The voucher supplier. The only network call any tool makes.
    • render.tsSix block kinds for the app, twelve components for the other surface.

05The API proxy

Three independent reasons the supplier API cannot be called from a browser.

The employee app reads everything else straight from the browser. The gift-voucher supplier’s API is the one exception, so a small Node proxy sits in front of it. It keeps both logins, does the AES encryption, holds the auth token for thirty minutes at a time, and hands the app four read-only routes on localhost.

The assistant never holds a credential. It calls one local endpoint and gets JSON back.

Scroll the diagram sideways

  • 01

    The key would ship in the page

    The API expects an AES-256-CBC encrypted body on its stock and voucher calls. Performing that in the browser would ship the key, the initialisation vector and the login to every employee who opens developer tools.

  • 02

    The egress IP is allowlisted

    The supplier rejects unrecognised origins with IP not whitelisted. A browser calls from whatever network the employee happens to be on, which no allowlist can enumerate.

  • 03

    CORS is closed

    The API sets no cross-origin headers for browser origins. With the first two conditions resolved, the request would still be blocked before dispatch.

06What the API taught me

Six supplier behaviours the integration guide does not document.

All six were found by running the integration against the live account. None is in the guide, and two contradict it.

A wrapper written from the documentation alone would have been confidently wrong in four places, and one of those would have double-spent.

  1. Issuing is asynchronous, and a non-zero code does not mean failure

    The first authorised live issue returned code “2812”, which appears in no error table, and no voucher. The order was queued, not rejected. The outcome is only knowable by polling the status call; reissuing the request purchases a second voucher. Poll, never retry. Nothing was consumed

  2. An error documented as one thing meant another

    The code the vendor’s own catalogue calls “inactive product” comes back over and over while an order is still settling. Read as a rejection, it would have killed good orders. It means pending. Contradicted the vendor’s own catalogue

  3. Settlement is inconsistent, so the client needs three states

    Four orders settled in eighty to a hundred seconds. The fifth returned immediately. So the client keeps three states, pending, issued and failed, and holds on to the order id to check back against. Why the schema carries three statuses, not two

  4. The stock call does not decrement

    Every brand reported unchanged availability after a successful purchase. It reports what the catalogue holds, not what has been set aside, so it cannot confirm a purchase and should not be read as a failure either. Two plausible inferences, both wrong

  5. The brand delivered is not always the brand ordered

    Three of six live orders were delivered under a brand other than the one requested. So the assistant checks what arrived against what was asked for, and warns with both names. The primary reason the assistant hands off rather than purchasing

  6. Published addresses were not usable

    The outlet records carry usable brand names and towns, and street addresses that do not resolve to real locations. The assistant names the town and never an address. The data decided the copy

07The data boundary

Two model calls, and only one of them transmits tool results.

One call sends the question. The other sends the tool result along with it, so the model can write a sentence about the data. Which one is running comes down to a single environment variable, and that is what to check first before believing anything on this page about what leaves the machine.

It runs on the server, over whatever the client sent, so a client that oversends cannot widen the boundary.

ANSWER_MODE

Crosses: the question, with email addresses and runs of ten or more digits stripped. Never crosses: a full voucher code, under either setting. The tool masks it before returning.

Held by

08The tools

Every tool hands back data, or the reason it has none.

Six things it will not do

  • It cannot actIt cannot book, buy, cancel, or change a declaration. Those tools were never written.
  • One currencyRupees and health coins never appear in the same answer.
  • No codesA voucher code is masked before the model ever sees it. Revealing one is a deliberate tap in the app.
  • No addressesThe supplier publishes none, so it names the town rather than inventing a location.
  • Live items onlyComing soon and not in your city are stated as facts, never offered as options.
  • No recallEvery answer comes from a lookup. If nothing fits, it says so rather than inventing.

One tool result, two surfaces, six block kinds

  • Header
    The figure or the subject on its own line, with its qualifier beneath rather than competing for the same line.App
  • Sentence
    The only part a model can replace, and only if every figure in it is in the data.Model, supervised
  • Note
    A caveat that must not be smoothed over: a voucher under the wrong brand, an order that never went through.App
  • Rows
    The data. Each row carries a validated route, so a result set behaves as a list of links.App
  • Follow-ups
    Written as complete questions, because no conversation state is retained between turns.App
  • Buttons
    Only to screens the app confirmed it has. No screen list means no buttons.App

09The fallback ladder

Four steps down, and the last one still answers from live data.

Every fallback in the first build guarded against faults in our own code. None guarded against the provider itself failing, which proved to be the more frequent condition. Both were observed in testing: an exhausted free-tier quota, and a model retired mid-project.

Quota is allocated per model, so a second model on the same key carries its own allowance, not a share of the first.

  1. Retry the same modelA rate limit, a timeout, a server errorA slower answer. It waits however long the provider asks for, not a fixed interval
  2. Try the second modelThe first is gone or retiredThe same answer, and no waiting, because retrying a retired model cannot work
  3. Keyword rulesEvery model failedA correct but narrower answer. The lookups still return live data, but fewer phrasings are understood
  4. Helpful fallbackNothing recognised the questionLive benefits as rows, category chips and a browse button, rather than a flat failure

10What I learned

Three conclusions.

  1. 01

    The bottleneck moved from writing code to verifying it

    Implementation stopped being the constraint. Establishing what was actually true, of the schema, of the supplier API, and of my own earlier decisions, did not get faster, and is now where the time goes.

  2. 02

    Two functions call a model; the rest is ordinary application code

    Routing and composition are the only model calls. Everything else is a route handler, a proxy, a switch statement and a renderer, and behaves identically whichever provider is configured.

  3. 03

    Integrate against the live API, not the document

    Four of the six supplier behaviours recorded in section 06 contradict its integration guide. Acting on one of them as documented would have issued a second voucher against a live account.
