conversational design

designing the conversation, not just the chat ui.

The interface was only one part of the experience. I had to design how the assistant understands intent, responds, guides the user and moves the conversation forward.

The prototype’s tools and renderer, running in this page. Routing here is the app’s keyword layer; in the app, the AI does that step.

  1. 01 · understand intent

    it asks instead of guessing

    “How much do I have left?”

    “Left” fits rupees and Health Coins alike, and the balance tool refuses to guess. A product rule: rupees and coins never appear in the same answer. So the question comes back as a choice, one chip per balance, and it names flexi, the third balance, which it can explain but can’t total.

  2. 02 · one tap moves it forward

    a chip is a whole question

    “How many coins do I have?”

    Each follow-up is written as a complete question, so it works on its own: 2,750 coins, what they are, and what to ask next.

  3. 03 · answer, then action

    a no that still goes somewhere

    “Can you cancel my gym booking?”

    It understood. Booking, buying and cancelling tools were never written, so it names exactly what it can’t do, and ends on the screen where cancelling happens, not on a no.

  4. 04 · structure the answer

    answer first, facts in rows

    “Tell me about Gym & fitness memberships”

    One line answers. Rows carry what it costs, how it’s paid for and who provides it, so no phrasing can drop a figure. The button opens the benefit’s own screen, where subscribing happens.

    data boundary

    the model doesn’t need to see everything.

    when the ai is unavailable

    four steps down, and the last one still answers.

    1. Retry the same modelA rate limit or timeout. A slower answer: it waits as long as the provider asks.
    2. Try the second modelThe first is gone or retired. The same answer, no waiting.
    3. Keyword rulesEvery model failed. A correct but narrower answer, still from live data.
    4. Helpful fallbackNothing recognised the question. Live benefits as rows and a way to browse, never a flat failure.

    A used-up quota and a model retired mid-project both happened in testing.

    found by running it

    reality doesn’t behave like documentation.

    Six supplier behaviours the integration guide doesn’t document, found by running the integration on the account I had access to.

    1. The order was queued, not rejected. Reissuing it buys a second voucher.

      Expected: a non-zero code means the order failed.

      Poll the status. Never retry.

    2. “Inactive product” comes back again and again while an order is still settling.

      Expected: it means rejected, as the vendor’s catalogue says.

      Read it as pending.

    3. Four orders took eighty to a hundred seconds. The fifth returned at once.

      Expected: orders settle the same way each time.

      Three states, pending, issued and failed, and keep the order id.

    4. Every brand reported the same stock after a purchase.

      Expected: stock goes down after a purchase.

      Stock never confirms or fails a purchase.

    5. Three of six orders arrived under a different brand.

      Expected: the brand delivered is the brand ordered.

      Check, warn with both names, and hand off instead of buying.

    6. Published store addresses don’t resolve to real locations.

      Expected: they are usable.

      Name the town, never an address.

    what i learned

    What I learned

    1. ai ux is behaviour design.

      The screen was the easy part. The work was deciding what the AI may decide, when it says no, and how a no still helps.

    2. the model shouldn’t own the product.

      It picks a tool. Facts, rules and every word of a refusal belong to the app, which is why an outage degrades the assistant instead of breaking it.

    3. building showed me what a static design couldn’t.

      Reading the live database first turned a spec for eighteen tools into eight. Three of six voucher orders arriving under the wrong brand reversed the plan to issue vouchers.

    4. building became faster. verification became harder.

      A respecification in the morning ran the same day. Finding out what was actually true, of the database, the supplier and my own decisions, did not speed up.

    5. fallbacks are part of the experience.

      The provider failing turned out more common than our own bugs: a used-up quota, and a model retired mid-project. The last rung still answers from live data.

    6. ai coding expanded my role as a designer.

      I owned the spec, the architecture, the rules and the standard for accepting a build, and Claude Code turned each decision into running code.

    from designing the interface to designing the entire product behaviour.
