01What I built

An informative assistant over thirteen tools, and the server behind it.

WorkPerks is a corporate benefits app. The assistant inside it answers three kinds of question: what the company offers, what a given benefit covers, and what you already have.

Three weeks of it went on finding where the build met the specification only on paper.

Claude Code wrote every line, and the three specification documents behind it. Section 03 is that process in brief; the detailed research study is all of it.

02Why I built it

Nobody types “Health & Clinical Care”. They type “my back has been hurting”.

The catalogue holds thirty-five benefits across ten categories, each with its own vendors, variants and funding rule. It is filed the way a benefits team thinks. People arrive with a situation instead: a sore back, a move to another city, a week of bad sleep.

The first version matched keywords, so a question had to already contain the catalogue’s own words. Back is not a category, and nor is tired.

Getting from what someone says to the words the catalogue uses is the only part worth a model. After that it is just a search.

03The method

Specify, build, run it against the live systems, then rewrite the specification.

Claude Code wrote all of it: the screen, the server, the thirteen tools, the proxy, the renderer, the tests, and the three rounds of spec that steered them. What I never did was ask for something and simply accept what came back.

  1. Read the live schema firstBefore a word of specification

    Revision one proposed eighteen tools. Ten of them already existed, and already did what it proposed to invent. Reading the database removed more than half the work and left eight to build.

  2. Write down what it cannot doRules, not preferences

    It cannot book, buy or cancel. It never mixes two currencies in one answer. It never reads a code out loud. Each rule moved from a line in a prompt to a check in the code, where a later change cannot quietly drop it.

  3. Build itClaude Code

    A rewritten spec in the morning came back working the same day. That speed is the only reason three rounds fitted into three weeks.

  4. Run it against the live database and the live supplier account

    Not test data. Six real voucher orders on a real account. What came back rewrote the spec twice, and reversed one decision completely.

  5. Hand the build to an agent with no stake in itNine defects

    One of them was a promise the spec made and the code did not keep. Every link was supposed to be checked before it was shown. Only the buttons were. The rows people actually tap went out unchecked.

  6. Generate the tests from the catalogueSo they cannot go stale quietly

    Every benefit, variant, category and funding type turns into questions on its own. Eleven flat rules then read each answer back: no two currencies together, no route that leads nowhere, no unmasked code.

04How it works

Five layers, and only one of them is allowed to contain a model.

The model decides which tool. The app decides what the answer looks like. Those two never swap. Every item below is a file or a service that exists in the build.

    Two surfaces, one server

    Chat.tsx the screen · chat.ts builds what gets posted with each question · chat-shim.js the older client

  2. API route

    Everything before a model runs

The one network call any tool makes

The app reads everything else straight from the browser. The gift-voucher supplier is the one exception, and the browser is shut out of it three separate ways.

It wants its requests encrypted, and doing that in a page would hand the key to anyone who opens developer tools. It only accepts known addresses, and people work from whatever network they happen to be on — it answers the rest with IP not whitelisted. And it never tells a browser it is allowed to call at all. Fixing any one of the three still leaves the other two.

So a small Node proxy holds both logins, does the encryption and caches the token. The assistant never holds a credential: it calls one local endpoint and gets JSON back.

Seven routes exist and the assistant reaches four. Issuing a voucher is the only write and the only POST, and no tool points at it.

What the live account taught me that the guide does not say

  1. A non-zero code does not mean failure

    The first authorised live issue returned code “2812”, which appears in no error table, and no voucher. The order was queued, not rejected, and the outcome is only knowable by polling. Retrying the request buys a second voucher. Poll, never retry. Nothing was consumed

  2. The brand delivered is not always the brand ordered

    Three of six live orders arrived under a brand other than the one requested. The specification had the assistant issuing vouchers itself; it now hands off to the voucher screen, and checks what arrived against what was asked for. The finding that reversed a decision

Four more are in the detailed research study. One of them is an error the vendor’s own documents describe as the opposite of what it really means. That page also covers what gets stripped out before the model sees anything, how each of the thirteen tools works, and what happens when a provider goes down.

06What I learned

Three conclusions.

  1. 01

    The bottleneck moved from writing code to verifying it

    Writing the code stopped being the slow part. Finding out what was actually true did not get any faster — true of the database, of the supplier API, and of decisions I had made myself a week earlier. That is where the time goes now.

  2. 02

    Two functions call a model; the rest is ordinary application code

    Picking the tool and phrasing one sentence are the only two things the model does. The rest is ordinary code, and it runs the same way whichever provider is plugged in.

  3. 03

    Integrate against the live API, not the document

    Four of the six supplier behaviours I recorded contradict its integration guide. Acting on one of them as documented would have issued a second voucher against a live account.
